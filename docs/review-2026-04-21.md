## คำตัดสินสรุป (TL;DR)

ระบบทำงานได้และโครงสร้างใหม่หลัง migrate สะอาดดี **แต่มีปัญหาความปลอดภัยระดับวิกฤติ 5 ข้อ ที่ต้องแก้ก่อนปล่อยให้คนใช้จริง** — ทุกข้อตรงกับ Phase 2 ใน Roadmap ของพี่อยู่แล้ว แค่ต้องเริ่มทำ

**ความเร่งด่วน 3 ระดับ:**

```
สัปดาห์นี้ (ก่อนใช้งานจริง)    → 5 ข้อระดับ CRIT (security)
เดือนนี้ (Phase 2 ของ Roadmap) → 6 ข้อระดับ HIGH + dead routes + getCase bug
ภายหลัง (Phase 1 + 3 ของ Roadmap)  → Refactor + Vue migration
```

## ส่วนที่ 2 — Security & PDPA Findings

### 🔴 CRITICAL (ต้องแก้ก่อนปล่อยใช้จริง)

| # | ที่ | ปัญหา | วิธีแก้ |
|---|-----|------|--------|
| **CRIT-1** | `gas-backend.gs:22` + `:186` | Password เก็บเป็น **plaintext** ใน Google Sheets และเปรียบเทียบแบบ string ตรง ๆ ใครเปิด Sheet เห็นรหัสทุกคน | ใช้ SHA-256 hash (ตัวอย่างโค้ดอยู่ใน Roadmap Phase 2.1) — hash ฝั่ง backend ก่อนเก็บ + เปรียบเทียบ hash |
| **CRIT-2** | `auth.js:18` | Password ส่งใน **URL query string** (`?password=...`) ทำให้ติดอยู่ใน browser history, server log, และ HTTP referrer | เปลี่ยนเป็น **POST request** + body JSON. แก้ทั้ง `gasCall()` และ `doLogin()` |
| **CRIT-3** | `gas-backend.gs:12, 22` | Default admin/1234 hardcode ไว้ในโค้ด **และในคอมเมนต์** ทุกคนที่อ่านโค้ดรู้ทันที | สุ่ม password ตอน setup + บังคับเปลี่ยนรอบแรก หรือถามตอน deploy |
| **CRIT-4** | `gas-backend.gs:260` (`handleGetCase`) | **ไม่มี authorization check** — ผู้ใช้คนใดก็เปิดคดีของคนอื่นได้ ถ้ารู้ caseId | เพิ่มเช็ค `caseRow.createdBy === username` ก่อน return (ยกเว้น admin) |
| **CRIT-5** | `gas-backend.gs:369` (`handleDeleteCase`) | **ไม่มี authorization check** — ใครก็ลบคดีของคนอื่นได้ | เช่นเดียวกับ CRIT-4: เช็คเจ้าของคดีก่อนลบ |

### 🟠 HIGH

| # | ที่ | ปัญหา | วิธีแก้ |
|---|-----|------|--------|
| HIGH-1 | `config.js:3` | `GAS_URL` เห็นได้ใน client code → endpoint backend เปิดเผยต่อสาธารณะ | ตอนนี้ GAS Web App "Anyone" อยู่แล้ว ดังนั้นแค่ซ่อน URL ไม่ช่วย — ต้องคู่กับ token-based auth (Phase 2.2) |
| HIGH-2 | `api.js:54-74` | localStorage offline cache เก็บ **caseData ทั้งก้อน** (ชื่อ, เลขบัตร, ที่อยู่) แบบ plaintext ในเครื่อง | เข้ารหัสก่อนเก็บ (Web Crypto API + key จาก password); หรือใช้ IndexedDB + library encryption |
| HIGH-3 | `gas-backend.gs:408` `handleListUsers()` | คืนรายชื่อผู้ใช้ทั้งหมดได้โดยไม่เช็คสิทธิ admin | เพิ่มเช็ค `requesterRole === 'admin'` |
| HIGH-4 | `api.js:37, 123` | ส่ง `username` กับ `caseId` ใน URL query เช่นเดียวกับ CRIT-2 | เปลี่ยนเป็น POST body |
| HIGH-5 | `sw.js:43-49` | Service Worker cache response จาก `script.google.com` แบบ network-first → ข้อมูลคดีอาจถูก cache บน disk | Whitelist: cache เฉพาะ static assets ห้าม cache response ที่มี `caseData` |
| HIGH-6 | `auth.js:6-14` | ถ้า `GAS_URL` ว่าง → "offline mode" รับ login อะไรก็ได้และให้ role admin | ใส่ PIN/master password สำหรับ offline mode หรือปิด offline mode ใน production |

### 🟡 MEDIUM / LOW

- **MED-1** `api.js:28` — โชว์ raw response ใน toast (อาจ leak error message ที่มี PII)
- **MED-2** `api.js:45-47` — เก็บรูปถ่ายเป็น base64 ใน Sheet cell (ชนลิมิต cell + ทำ Sheet ช้า) → แนะนำเก็บใน Drive แทน
- **MED-3** `gas-backend.gs:79` — `catch(err)` คืน `err.message` ตรง ๆ → leak stack trace
- **LOW-1** `api.js:25-28` — ไม่เช็ค HTTP status ก่อน parse JSON → silent fail บน 5xx

### PDPA Compliance Gaps

1. **ไม่มี audit log** ว่าใครเปิด/แก้/ลบคดีของใครเมื่อไหร่ — PDPA ต้องการ accountability
2. **ไม่เข้ารหัสข้อมูลส่วนบุคคล at-rest** ทั้งใน Sheets และ localStorage
3. **ไม่มี data retention policy** — คดีเก่าอยู่ใน Sheet ตลอดไป
4. **ไม่มีระบบ consent / acknowledgement** ของเจ้าหน้าที่ก่อนใช้งาน
5. **Data minimization** — เก็บ field มากกว่าที่จำเป็น (เช่น passport ถ้าไม่ได้ใช้)

## ส่วนที่ 3 — API Contract Audit

ผลรวม: 5 actions ใช้งานจริง + 2 routes ฝั่ง backend ที่ frontend ยังไม่เรียก

| Action | Frontend → Backend | สถานะ |
|--------|---------------------|--------|
| `login` | `auth.js:18` → `handleLogin` | ✅ ตรงกัน (แต่มี security issue ดู CRIT-2) |
| `listCases` | `api.js:37` → `handleListCases` | ✅ |
| `getCase` | `api.js:123` → `handleGetCase` | ⚠️ **API-1** ดูด้านล่าง |
| `deleteCase` | `api.js` → `handleDeleteCase` | ✅ shape ตรง / ❌ ไม่มี authz (CRIT-5) |
| `saveCase` | `api.js:90` → `handleSaveCase` | ⚠️ **API-2** ดูด้านล่าง |
| `listUsers` | — ไม่มี | 🟡 dead route (Phase 2.3 จะใช้) |
| `addUser` | — ไม่มี | 🟡 dead route (Phase 2.3 จะใช้) |

**API-1 (HIGH):** ตอนนี้ frontend (`api.js:124`) อ่าน `data.caseData` ตรง ๆ แต่ตามที่ audit subagent รายงาน backend อาจ wrap ใน `data.case.caseData` — **ต้องเปิด `handleGetCase` ใน gas-backend.gs ดูชัด ๆ ก่อนแก้** (ไม่ได้ verify ในรายงานนี้ ขอแนะนำให้พี่ลองเรียกจริง 1 ครั้งแล้วดูว่า payload หน้าตาเป็นยังไง)

**API-2 (MED):** `saveCase` รับ `data.user` แต่ไม่มี validation ว่าไม่ว่าง — frontend ส่ง `S.currentUser?.username || ''` แทน ซึ่งอาจส่งสตริงว่างถ้า session หมด

3. **แยก `renderPhotoGrid(suspects, role)` เป็น helper เดียว** — ตอนนี้มี 2 implementation (12 นาที)

**Top refactor (medium effort):**

แยก `buildDocHTML` ออกเป็น 3 ฟังก์ชัน + shared partials:

## ส่วนที่ 5 — Sprint Plan แนะนำ (สัปดาห์หน้า)

ทำตามลำดับนี้ในสัปดาห์เดียว — แต่ละข้อใช้เวลา ~1-3 ชม.

```
Day 1 — Git + Audit log skeleton
  □ git init + .gitignore + first commit (Phase 1.2)
  □ เพิ่ม sheet ใหม่ "AuditLog" headers: [timestamp, user, action, caseId, result]
  □ เพิ่มฟังก์ชัน logAction() ใน gas-backend.gs (ยังไม่ต้องเรียกที่ไหน)

Day 2 — CRIT-1: Hash passwords
  □ เพิ่ม hashPassword() ใน gas-backend.gs (SHA-256)
  □ Migration script: hash password เก่าทุกคนใน Users sheet 1 ครั้ง
  □ แก้ handleLogin ให้เปรียบเทียบ hash
  □ ทดสอบ: login ด้วย admin/1234 ยังเข้าได้ (หลัง migrate)

Day 3 — CRIT-2: POST-based login
  □ เพิ่ม doPost() ใน gas-backend.gs ที่รับ JSON body
  □ แก้ gasCall() ให้รองรับทั้ง GET และ POST
  □ แก้ doLogin() ใช้ POST
  □ ทดสอบ: ดู Network tab ใน DevTools — password ต้องไม่อยู่ใน URL

Day 4 — CRIT-4 + CRIT-5: Authorization checks
  □ ทุก handler ที่อ่าน/เขียน case → เช็ค createdBy ก่อน
  □ ถ้า role !== 'admin' && createdBy !== requestUser → return error
  □ ทดสอบด้วย user 2 คน

Day 5 — CRIT-3: Default password rotation
  □ ตอน initSheets() ถ้าเป็นรอบแรก → สุ่ม password ใส่ Logger.log()
  □ ลบ comment ที่บอก default credentials
  □ บันทึกไว้ใน docs/SETUP.md ใหม่ — ดู Logger หา password รอบแรก

Day 6-7 — Verify + commit
  □ ทดลองใช้จริงครบทุก flow
  □ Commit แต่ละขั้นแยกกัน (5-7 commits)
  □ Tag v1.1-security
```

หลังสัปดาห์นี้ → CRIT ทั้ง 5 ปิดหมด → พร้อมเปิดให้คนอื่นใช้

จากนั้นค่อยไปต่อ HIGH (Service Worker cache, localStorage encryption, listUsers authz) แล้ว Admin Panel UI (Phase 2.3) แล้วค่อย refactor + OCR feature

## ส่วนที่ 6 — สิ่งที่ผู้ตรวจไม่ได้เช็ค (ขอแนะนำ)

- Browser ทดสอบจริงบน Chrome/Edge/Safari — ยังไม่ได้รัน
- Performance — ขนาด `documents.js` 40KB อาจช้าตอน load บนมือถือเก่า
- รูปภาพถ่ายหลายรูป → memory ในมือถือ
- พฤติกรรม Service Worker เมื่อมีอัพเดทใหม่ (cache busting)
- ทดสอบกับ Google Apps Script quota จริง (6 นาที/execution, 30 ครั้ง/นาที)
